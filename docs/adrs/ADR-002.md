# ADR-002 - Monorepo Poliglota

- **Data**: 2026-09-07
- **Deciders**: @pedro-fs-garcia

## Contexto

O Synapse tem quatro componentes de desenvolvimento em stacks distintas — `frontend` (Vue), `api` (Spring Boot), `codegen` (Python/LangGraph) e `worker` (linguagem ainda não definida) —, mais a imagem do sandbox e os serviços de infraestrutura (ADR-001). Era preciso decidir se o código ficaria num repositório único ou em repositórios separados por componente.

Quatro forças condicionam a escolha:

1. **Os contratos abrangem todos os componentes e ainda estão sendo descobertos.** O catálogo de eventos, a representação da regra e os contratos de mensageria mudam a cada sprint, cada um com produtor e consumidor em stacks diferentes. O caso mais acoplado é o schema do banco de dados: a `api` é dona das migrations **das tabelas que `worker` e `codegen` escrevem**.
2. **A implantação é por host separado** (ADR-001), o que permite defasagem de versão em runtime e um serviço pode subir com um contrato que o outro ainda não entende.
3. **O uso de IA no desenvolvimento é obrigatório** (requisito Fatec/Dom Rock). Uma ferramenta que enxerga apenas metade de um contrato não conduz mudanças que o atravessam.
4. **A entrega acadêmica inclui um Manual de Instalação** que precisa levar um avaliador do zero ao sistema rodando.

## Decisão

Adotamos **um monorepo poliglota**, com um diretório por componente e **sem ferramenta de build de monorepo**. Cada serviço mantém o layout que teria caso estivesse em um repositório isolado (ex.: `package.json` na raiz do `frontend`, `pom.xml` na da `api`, `pyproject.toml` na do `codegen`, e o manifesto nativo do `worker` quando sua linguagem for definida). A implantação continua por host separado, como decidido no ADR-001.

| Na raiz | Em cada componente |
| --- | --- |
| `contracts/` (schemas de evento, domínio, HTTP e observabilidade), `.agents/`, `.github/workflows/`, `.githooks/`, `docs/`, `deploy/`, `.dockerignore` | Manifesto nativo da stack, `Dockerfile`, `verify.sh`, `AGENTS.md` e configuração de IDE |

Especificações que compõem a decisão:

- **Um serviço por PR.** Fluxo de CI e hooks de pré-commit impõem que nenhuma alteração toca dois componentes no mesmo PR.
- **Evolução aditiva de contrato.** Campo entra opcional (fora de `required`), nunca é removido nem renomeado; consumidores ignoram campo desconhecido, e schemas de evento não usam `additionalProperties: false`. Sem isso, a regra anterior força um estado intermediário quebrado.
- **`contracts/` é insumo de build, não dependência de runtime.** Os schemas são copiados para dentro de cada artefato durante o build; nada é importado entre diretórios. Os DTOs são escritos à mão na stack de cada componente, e um teste por componente desserializa `contracts/examples/` nesses DTOs.
- **Contexto de build na raiz** — `docker build -f <componente>/Dockerfile .`, para alcançar `contracts/`.
- **Verbo `verify` uniforme.** Cada componente expõe um `verify.sh`; hook, máquina do dev e CI chamam o mesmo comando, e o despacho é por caminho alterado. A interface é uniforme; a implementação é a da stack de cada um.
- **Verificação centralizada, implantação separada.** A CI de verificação é um workflow que sempre roda, com jobs condicionais por componente e um job agregador como único check obrigatório; os deploys são um workflow por componente, com filtro de caminho.
- **Imagens etiquetadas com o SHA do commit**, para que o conjunto de versões compatíveis seja identificável apesar do deploy independente.

Nada nesta decisão depende da linguagem de um componente específico: como a raiz não adota os projetos, a escolha da stack do `worker` não a altera, e um componente pode inclusive trocar de linguagem sem que o arranjo mude.

### O diretório `contracts/`

É o principal ativo que a decisão viabiliza, e por isso seu formato faz parte dela. O conteúdo é **JSON Schema** (draft 2020-12) — deliberadamente neutro em relação às stacks: não há dono natural, já que `simulacao-concluida` é produzido por um serviço e consumido por dois outros, em linguagens diferentes.

```
contracts/
├── events/          uma mensagem por arquivo: regra-submetida, executar-codigo,
│                    parametros-confirmados, simulacao-concluida, no-concluido, etapa-alterada
├── domain/          representacao-regra, resultado-simulacao
├── http/            openapi.yaml (superconjunto de JSON Schema; referencia os arquivos acima)
├── observability/   atributos obrigatórios de log e trace (job_id, no, competencia)
└── examples/        um exemplo válido por schema — é o que os testes consomem
```

```json
// contracts/events/simulacao-concluida.schema.json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object",
  "required": ["job_id", "resultado_id", "status", "veredito"],
  "properties": {
    "job_id":         { "type": "string", "format": "uuid" },
    "resultado_id":   { "type": "string", "format": "uuid",
                        "description": "Linha da tabela de resultado; o evento carrega a referência, não o conteúdo" },
    "status":         { "enum": ["sucesso", "erro_codigo", "erro_infra"] },
    "veredito":       { "enum": ["viavel", "inviavel", "indeterminado"] },
    "total_simulado": { "type": "number" }
  }
}
```

```json
// contracts/examples/events/simulacao-concluida.json
{
  "job_id": "3f2b1c40-0d18-4a51-9f2e-6c1d9a77b021",
  "resultado_id": "b81e0f4c-52a9-4f0b-8a3d-7c2e5d10ab93",
  "status": "sucesso",
  "veredito": "inviavel",
  "total_simulado": 184320.55
}
```

Quatro regras de escrita que decorrem do que já foi decidido acima:

- **Sem `additionalProperties: false`** nos eventos: com deploy por host, um produtor novo emitindo campo novo não pode quebrar um consumidor antigo.
- **Opcional é ausência, não `null`.** Campo novo entra fora de `required`, com tipo simples. "Ausente" significa *este produtor ainda não emite*; `null` significaria *emitiu e não há valor* — e colapsar os dois apaga a informação. Como `record` em Java não distingue ausente de nulo, proibir `null` faz essa limitação não custar nada.
- **`description` não é enfeite.** O schema do resultado é inserido no prompt do `codegen` para descrever a saída que o código gerado precisa produzir; o texto ali é lido pelo modelo.
- **`default` é anotação, não comportamento** — validador nenhum preenche campo ausente. O default real mora no DTO de cada componente.

### O harness de IA

O uso de IA no desenvolvimento é obrigatório, e em repositórios separados isso significaria **quatro harnesses**, com convenções duplicadas divergindo entre eles e nenhum lugar onde as verificações entre componentes pudessem ficar. O repositório único torna o harness **um só**. Mas um harness único não é um conjunto único de regras: regra que vale para Vue não vale para Spring Boot. Ao mesmo tempo que as regras para mensagens de commit são transversais. A forma correta é **espinha compartilhada na raiz, conteúdo por componente**.

```
AGENTS.md                 espinha: domínio, invariantes, mapa dos componentes
.agents/
├── conventions/          commit, PR, numeração de ADR, definição de pronto
└── skills/               fluxos que atravessam componentes

<componente>/AGENTS.md    regras de stack e de segurança daquele serviço
<componente>/.agents/skills/
```

| Camada | Escopo | Por quê |
| --- | --- | --- |
| Convenções e contexto do sistema | Raiz | Independem de stack; é o que diverge se cada componente decidir sozinho |
| **Regras de stack e de segurança** | Componente | É onde mora o valor, e é o que não pode ser genérico |
| Gates de verificação | Componente, com despacho na raiz | Comandos distintos; compartilha-se *quando* rodam, não *o que* rodam (ver `verify.sh` acima) |
| Checks entre componentes | Raiz | Só existem porque o repositório é único |

As regras por componente são de segurança do projeto, não de estilo — e é por isso que não podem ser fundidas num arquivo só: o `codegen` não emite número apurado e trata a transcrição como dado, nunca como instrução; o `worker` não roda código gerado fora do container nem relaxa flag de isolamento; a `api` grava job e evento de outbox na mesma transação e não escreve em tabela de outro serviço; o `frontend` não contém lógica de negócio nem calcula valor exibido.

As **skills seguem o alcance, não o assunto**: na raiz ficam as que atravessam componentes — "adicionar campo a um evento" (produtor, consumidor e o schema em `contracts/`) e "criar migration" (que precisa lembrar do `GRANT` do serviço que vai escrever, seção 6.2 do ARCHITECTURE.md); no componente ficam as que não saem dele. As duas primeiras são exatamente o que repositórios separados impediriam de escrever, porque exigem enxergar os dois lados do contrato.

Duas disciplinas sustentam o arranjo: o `AGENTS.md` da raiz é carregado em toda tarefa de todo componente, então deve conter mapa e invariantes, com o detalhe descendo para skill que carrega sob demanda; e a interoperabilidade entre ferramentas (Claude Code, Codex, Cursor, Antigravity) se resolve com **um arquivo canônico por diretório**, com os demais nomes apontando para ele — cópias divergem na terceira semana.

## Consequências

**Positivas**

- `contracts/` não precisa de mecanismo de distribuição: nem submódulo, nem publicação de pacote nos ecossistemas de cada stack.
- A CI verifica os dois lados de uma mudança de contrato **antes do merge** — o PR que altera um schema roda o teste do consumidor que ainda não foi tocado.
- Um commit identifica o conjunto compatível de versões, o que importa porque a implantação por host permite defasagem.
- Convenções, catálogo de eventos e `AGENTS.md` da raiz existem em cópia única.
- A ferramenta de IA lê o outro lado do contrato mesmo alterando um serviço só, e fluxos que atravessam componentes tornam-se executáveis numa sessão.
- O Manual de Instalação é um clone e um comando.
- A saída é barata: separar em repositórios depois é `git filter-repo` preservando histórico, enquanto o caminho inverso exigiria fundir históricos.

**Negativas**

- **Armadilha dos checks obrigatórios**: filtro de caminho combinado com branch protection trava PRs esperando um check que nunca vai rodar. É complexidade acidental, existe só por causa do monorepo e não compra nada; contornada pelo job agregador.
- O painel de Git mostra o repositório inteiro, e *Stage All Changes* commita arquivos de outro serviço. Mitigado por hook e CI, não por atenção.
- Complexidade de montagem: hook com despacho, `paths-filter`, job agregador e `.dockerignore` — cerca de 50 linhas escritas uma vez. É custo de montagem, não de operação, mas é real.
- Todos clonam `dataset_domrock/`, mesmo quem nunca vai tocá-lo.
- Trabalhar com a pasta de um componente aberta na IDE abre mão de enxergar os outros — recuperável abrindo o workspace multi-root, e de impacto pequeno porque os componentes trocam mensagens, não símbolos.

## Alternativas consideradas

- **Repositórios separados por componente**: rejeitado  
    Vence em dois pontos reais — cada esteira de CI fica trivial e o painel de Git nunca mostra o serviço alheio —, mas perde no que pesa nesta fase: `contracts/` exigiria submódulo ou publicação de pacote em cada ecossistema; a compatibilidade entre produtor e consumidor só seria verificável depois de publicar o pacote e abrir o PR de bump; e a complexidade seria paga **por mudança**, indefinidamente, em vez de uma vez na montagem. Registro honesto: o argumento da mudança atômica foi retirado durante a análise, porque a regra de um serviço por PR torna a mudança atômica indesejada de qualquer modo.

- **Monorepo com ferramenta de build (Bazel, Nx, Pants)**: rejeitado  
    Resolve grafo de dependências entre dezenas de pacotes, problema que quatro serviços independentes não têm, ao custo de uma camada que todo o time precisaria aprender.

- **Publicar `contracts/` como pacote versionado, mesmo dentro do monorepo**: rejeitado  
    Desfaz o que o monorepo compra: a `api` poderia declarar contracts 1.2 enquanto o `worker` declara 1.1, e a defasagem de versão voltaria — escondida num arquivo de dependências em vez de visível no histórico.
