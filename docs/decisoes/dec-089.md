# DEC-089: Nomenclatura e Argumentos da Topologia do RabbitMQ

## Decisão

**Filas simples** - `regra-submetida`, `parametros-confirmados`, `etapa-alterada`, `no-concluido` - têm o mesmo nome da mensagem que carregam.

**A exchange fanout de `simulacao-concluida`** leva o nome da mensagem. Cada consumidor liga a ela uma fila própria, no padrão `simulacao-concluida.<consumidor>`: `simulacao-concluida.api` (api, T-088) e `simulacao-concluida.codegen` (codegen, T-049).

Toda fila e a exchange são **duráveis**, sem `exclusive`, sem `auto-delete` e sem nenhum argumento `x-*`. A declaração é **idempotente**: cada serviço declara o próprio lado ao subir, sem assumir que é o primeiro nem que é o único.

## Justificativas

* **Fila = nome da mensagem já era o padrão.** O worker (T-010, DEC-088) declarou `executar-codigo` com esse critério antes de existir qualquer outra fila no sistema. Estender o mesmo critério às quatro filas simples da api evita uma segunda convenção para o mesmo tipo de coisa.
* **`<mensagem>.<consumidor>`, não `<consumidor>.<mensagem>`.** Com dois consumidores independentes na mesma exchange, agrupar pelo nome da mensagem mantém as duas filas visíveis lado a lado no painel do RabbitMQ (`simulacao-concluida.api`, `simulacao-concluida.codegen`), em vez de espalhadas entre `api.*` e `codegen.*` junto de filas de outros assuntos.
* **Idempotente, nunca exclusiva.** `api`, `codegen` e `worker` sobem de forma assíncrona e a ordem entre eles não é garantida (mesmo raciocínio do DEC-088 para `executar-codigo`). Uma declaração que falhasse ao encontrar a exchange ou a fila já criada por outro serviço amarraria a inicialização a uma ordem de boot específica - o que o desenho assíncrono existe para evitar.
* **Sem argumento `x-*`.** Nenhum requisito até aqui pede TTL, dead-lettering ou prioridade nessas filas. Declarar sem argumento extra é o que torna a declaração idempotente entre serviços: o AMQP trata como equivalente uma redeclaração com os mesmos parâmetros, e rejeita com `406 PRECONDITION_FAILED` uma que diverge - um argumento que só um dos três serviços conhecesse quebraria essa equivalência em silêncio, até o dia em que a ordem de boot mudasse.

## Alternativas consideradas

| Alternativa | Por que não |
| :--- | :--- |
| **`<consumidor>.<mensagem>`** (`api.simulacao-concluida`, `codegen.simulacao-concluida`) | Agrupa por serviço em vez de por mensagem, e quebra o critério já em uso para as filas simples (`executar-codigo`, e agora `regra-submetida`, `parametros-confirmados`, `etapa-alterada`, `no-concluido`), que é sempre o nome da mensagem. |
| **Fila exclusiva por serviço, declaração falha se já existir** | Amarraria a inicialização dos três serviços a uma ordem de boot específica, incompatível com o desenho assíncrono (ADR-001) e com o fato de que nenhum dos três depende do outro para subir. |

## Consequências

* T-049 (codegen) e T-063/T-067 (worker) declaram a topologia usando exatamente estes nomes e estes argumentos. Um serviço que declare a mesma fila ou exchange com um argumento divergente (por exemplo, um TTL) recebe `406 PRECONDITION_FAILED` do broker ao subir, não uma perda silenciosa de mensagem.
* Renomear uma fila ou a exchange depois que os três componentes existirem exige coordenar os três ao mesmo tempo - um nome divergente entre os lados faz a mensagem se perder em silêncio, sem erro em nenhum processo, porque cada lado passa a falar com uma fila diferente sob o mesmo nome de mensagem.
* A api implementa o lado dela em `RabbitTopologyConfig` (T-088): as quatro filas simples, a exchange fanout e a fila `simulacao-concluida.api`, com uma declaração forçada na subida para que a topologia apareça imediatamente, sem depender de alguém publicar ou consumir primeiro.
